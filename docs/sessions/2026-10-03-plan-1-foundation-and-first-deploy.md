# 2026-10-03 — План 1 «Фундамент»: от идеи до прода на panel.159.team

## Итог

За одну сессию проект прошёл путь от пустого репозитория до работающей панели на **https://panel.159.team**
с автодеплоем при пуше в `main`. Реализован весь план 1: вход и управление админами, глобальный аудит,
типизированные настройки в БД с разделом в админке, layout с навбаром, Docker, CI, e2e. Сверху добавлены
доработки UI по живому фидбеку и прод-инфраструктура (сервер, Cloudflare Tunnel, DNS, GitHub Actions).

Telegram-часть (аккаунты из tdata, коды, QR-вход) и пул прокси — планы 2 и 3, ещё не начаты.

## Цель проекта (со слов владельца)

Веб-панель для своих Telegram-аккаунтов: аккаунты переносятся из portable Telegram Desktop `tdata`
(zip-архивы через upload), панель собирает сообщения из служебного чата с кодами входа (777000) всех аккаунтов
в одном месте и дублирует новые коды в приватный Telegram-канал через бота. Плюс пул прокси (прокси на аккаунт,
опционально, с проверкой здоровья и автосинхронизацией с proxy-store), статус/профиль/активные сессии аккаунтов,
вход новой сессией по QR, несколько равноправных админов с глобальным аудитом, настройки — в БД, а не в `.env`.

## Ключевые решения владельца

- Стек: TS/JS; React + Vite SPA; **весь UI — только shadcn/ui (Base UI)**; верхний navbar с табами, без sidebar
  (на мобиле — Sheet); тексты UI на русском.
- PostgreSQL 18, Redis 8, образ `node:26-trixie-slim`, всё в Docker; имена ресурсов с префиксом `accs-`.
- Архитектура B: API и воркер — отдельные процессы (воркер — план 2).
- Настройки: все неинфраструктурные — типизированные в БД с UI («своя реализация на реестре Zod 4»);
  в `.env` только инфраструктура.
- Прокси: на аккаунт, необязательный; при отказе прокси — предупреждение и остановка сессии до починки/замены
  или явного разрешения работать без прокси. Ручной ввод, импорт списков и отдельный авто-список из proxy-store
  (фильтр `country=kz`, `category=for_all`). Для спайка владелец даст 5 http + 5 socks прокси.
- Библиотека Telegram: mtcute (`@mtcute/convert` читает tdata; спайк на реальной tdata прошёл).
- Тема: сначала blue+mist, затем по просьбе владельца — **стандартная нейтральная** shadcn + переключатель
  светлая/тёмная/системная.
- Домен **159.team** (Cloudflare): панель на `panel.159.team`, API на том же origin (`/api`), apex пустой.
- Деплой: автоматически при пуше в `main`, **SSH из GitHub Actions** ключом с forced command;
  публикация через **отдельный именованный Cloudflare Tunnel** (по образцу p2c-pgon).

## Как шла работа

1. **Брейнсторм → спека → план.** Спека `docs/superpowers/specs/2026-10-03-accs-manager-design.md`,
   план `docs/superpowers/plans/2026-10-03-plan-1-foundation.md` (18 задач). Код плана сначала написан и прогнан
   в песочнице (80 vitest + 12 e2e + Docker), каждая задача проверена отдельно, и только потом записан в план.
2. **Исполнение — subagent-driven development** в ветке `feat/plan-1-foundation`: на каждую задачу свежий
   исполнитель, затем ревью (spec + качество), раунды правок, повторное ревью. Почти каждая задача получила
   один раунд правок по ревью. Существенное сверх плана:
   - `TRUST_PROXY` — `z.stringbool()` (строка `'false'` раньше давала `true`);
   - защита от `__proto__` в валидации настроек;
   - шина событий изолирует упавшие async-обработчики;
   - SettingsService: сериализованный reload, подписка до первой загрузки, ошибки после коммита не откатывают сохранение;
   - IP клиента за прокси — **крайний правый** адрес `X-Forwarded-For` (в спеке было «первый» — подделываемо);
   - вход: атомарное резервирование попыток (INCR до argon2), троттлинг смены пароля, advisory lock при отключении
     админа, смена пароля + отзыв сессий в одной транзакции;
   - аудит: сначала редактирование секретов, потом обрезка; тела > 64 КБ не читаются;
   - CLI: секретные настройки только через `--value-stdin`;
   - web: глобальный обработчик 401 → /login, сброс диалогов с паролями при закрытии.
3. **Финальное ревью всей ветки (opus)** — 5 важных находок, все исправлены одним заходом, повторное ревью чистое:
   SSE-поток жил после отзыва сессии; не было лимита тела запроса (1 МиБ); NUL/одиночные суррогаты в теле позволяли
   провести действие мимо аудита; перезапуск Postgres ронял API (нет `pool.on('error')`; заодно из ошибки pg
   вычищается объект клиента с паролем БД); настройки не перечитывались после переподключения Redis.
   Попутно найден и исправлен серьёзный баг: drizzle `jsonb` парсил строку второй раз, и значения вроде
   `"-1001234567890"`, `"0.25"`, `"true"` читались числом/булевым → настройка молча откатывалась к умолчанию
   (свой тип колонки `jsonb`, миграция не нужна).
4. **Доработки UI по фидбеку владельца** (после плана):
   - стандартная тема + переключатель темы одной строкой иконок в меню профиля, без мигания при загрузке;
   - favicon 🔑 inline SVG (base64);
   - пояснения ко всем настройкам: строка под названием + ⓘ-popover (наведение на десктопе, тап на мобиле;
     клик после наведения закрепляет, а не закрывает); единицы у числовых полей со склонением («30 дней»,
     «3 проверки»), явный диапазон «В днях: от 1 до 3650.»; длительности словами («от 1 минуты до 1 дня»);
   - `notify.chatId` принимает только полный ID на `-100…` (web.telegram.org/k показывает ID канала без префикса);
   - заголовки вкладок: «Панель | 159.team» по умолчанию, «Аудит | 159.team», «Уведомления — Настройки | 159.team»;
   - меню профиля шире;
   - вместо белого экрана — экраны «Не удалось загрузить страницу» (с «Повторить»/«Обновить») и «Страница не найдена»;
     автоперезагрузка при устаревших чанках ограничена по времени (раньше — один раз на вкладку).
5. **Telegram-бот и канал** проверены через Bot API: бот — админ приватного канала с правом публикации,
   тестовое сообщение доставлено. Токен в репозиторий не попадал; вводится в панели («Настройки» → «Уведомления»).
6. **Релиз и деплой** — см. ниже.

## Релиз и прод

- Перед первым пушем вся git-история проверена на секреты (токены, ключи, `.env`, tdata, пароли) — чисто.
  `feat/plan-1-foundation` влит fast-forward в `main` и запушен; ветка удалена.
- Первый CI на GitHub упал на e2e: ⓘ-кнопка с подписью «Подробнее: Хранить коды» дала второе совпадение
  для `getByLabel('Хранить коды')` → `{ exact: true }`. Урок: после изменений UI гонять e2e до пуша.
- CI: `checks` → `e2e` → `publish` (образ в GHCR `ghcr.io/nokimaro/accs-manager:<sha>` и `:main`) →
  `deploy` (environment `production`, только `main`): SSH ключом, который может только `deploy <sha>`,
  затем ожидание `https://panel.159.team/api/healthz` с `version` = коммит.
- Сервер — staging-бокс HOSTKEY, общий с p2c (адрес — `gh variable get DEPLOY_HOST --env production`).
  Снаружи открыт только SSH (ключи + fail2ban). Создан пользователь `accs-deploy` (docker), `/opt/accs-manager`
  (клон репо, `.env` 600 с секретами, сгенерированными на сервере), forced command `/usr/local/bin/accs-deploy-ssh`.
- Cloudflare: туннель `accs-manager` (id `2c394400-9bae-48b4-85ab-1c222eda90a3`), юнит `cloudflared-accs`,
  метрики `127.0.0.1:20243`, drop-in для `cloudflared-update`; CNAME `panel.159.team` → туннель.
  Сертификат зоны 159.team — `~/.cloudflared/cert-159team.pem` на машине разработчика (`cert.pem` там — sbpredator,
  его не трогать).
- Проверено на проде: деплой зелёный, `healthz` отдаёт sha, cookie `HttpOnly; Secure; SameSite=Strict`,
  аудит пишет реальный IP клиента (не адрес туннеля), API слушает только `127.0.0.1:3300`,
  туннели и контейнеры p2c не затронуты (4/4 соединения, без рестартов).
- Первый админ `admin` создан через CLI, пароль передан владельцу (сменить после входа).

Подробности и команды — `deploy/README.md` и `AGENTS.md`.

## Уроки и грабли

- pnpm 12: `minimumReleaseAge` → ставить пакеты мажорными диапазонами (`'pkg@^N'`); в Node 26 нет corepack.
- Порты 5432/6379/3000 на машине разработчика и 3000/3001/3100 на сервере заняты другими проектами.
- Base UI в jsdom: меню после закрытия не открывается повторно кликом в том же тесте — открывать через `defaultOpen`;
  `Button` с `render={<Link/>}` имеет роль `button`.
- Popover с `openOnHover`: клик по триггеру после наведения закрывал его — нужна своя логика «закрепления».
- Vite dev перестраивает зависимости при появлении нового импорта → перезагрузка вкладки; без экрана ошибки это
  выглядело как белый экран.
- Playwright `getByLabel` по умолчанию ищет подстроку — для полей с одноимёнными подсказками нужен `exact`.
- `cloudflared tunnel login` не перезаписывает существующий `cert.pem` — старый надо отодвинуть и потом вернуть;
  сертификат привязан к зоне, выбранной при логине.
- wrangler OAuth истёк; токена Cloudflare на сервере нет — для туннеля/DNS хватило `cloudflared` с сертификатом зоны.
- zsh раскрывает `?` в URL без кавычек.

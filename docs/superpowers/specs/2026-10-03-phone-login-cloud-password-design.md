# Вход по номеру и облачный пароль — дизайн

- **Дата:** 2026-10-03
- **Статус:** согласован с владельцем по частям, ожидает ревью спеки
- **Основная спека:** `docs/superpowers/specs/2026-10-03-accs-manager-design.md`. Этот документ её дополняет; где он молчит, действует основная спека.

## 1. Зачем

### Вход по номеру

Владелец хочет добавлять аккаунты новой сессией со своим api_id, когда активная сессия есть только в Telegram Desktop на Windows. Вход по QR в этом случае невозможен: Telegram Desktop не подтверждает QR-входы.

Проверено по исходникам tdesktop:
- метод `auth.acceptLoginToken` есть только в схеме протокола и нигде не вызывается;
- ссылки `tg://login` обрабатываются только с `?code=`.

Сканировать QR для подключения устройства умеют только мобильные приложения. Поэтому нужен стандартный вход по номеру:
1. Telegram присылает код в уже открытые приложения, обычно в Desktop сообщением от «Telegram»;
2. админ вводит код в панели;
3. если включён облачный пароль (2FA) — вводит и его.

### Облачный пароль

Для аккаунтов, уже добавленных в панель, нужно:
- ставить и менять облачный пароль;
- хранить его и показывать в карточке;
- показывать почту восстановления, если она привязана.

## 2. Решения владельца

| Вопрос | Решение |
|---|---|
| Аккаунт из входа по номеру уже есть в панели | Отказ, как в QR. Новая сессия сразу выходит, админ видит «Этот аккаунт уже есть в панели». |
| Хранение облачного пароля | Зашифрованным `APP_ENCRYPTION_KEY`, как прочие секреты; в карточке — показ по кнопке. Открытым текстом не храним. |
| Почта восстановления | Необязательный шаг при установке и смене пароля, его можно пропустить. Уже привязанная почта показывается в карточке. |
| Устройство | Вариант «А» (вход по номеру — отдельный поток по образцу QR) с общим модулем для обоих входов. Управление паролем — команды воркеру с ответом. |

## 3. Данные и секреты

### Поле в БД

Миграция `0003` добавляет `accounts.cloud_password_enc text null` — облачный пароль, если панель его знает. Источники:
- пароль введён при входе по номеру;
- пароль введён при входе по QR;
- пароль установлен или сменён через панель;
- админ ввёл текущий пароль, и Telegram его подтвердил.

Пишет поле только воркер и только после того, как Telegram подтвердил операцию. API только расшифровывает пароль для показа и шифрует его для передачи в воркер.

### Остальное про 2FA в БД не хранится

Воркер спрашивает у Telegram при открытии блока в карточке (`account.getPassword`):
- есть ли пароль, подсказка;
- `hasRecovery` (привязана ли почта восстановления);
- `emailUnconfirmedPattern` (маска неподтверждённой почты);
- `pendingResetDate` (дата отложенного сброса пароля).

Сам адрес почты восстановления Telegram отдаёт только `account.getPasswordSettings` и только с текущим паролем. Поэтому адрес показывается, лишь когда панель знает пароль.

### Секреты в пути

Код входа, облачные пароли и код из письма:
- **во входе по номеру** идут через приватный Redis-канал входа `accs:login:<id>` и нигде не хранятся (как пароль 2FA при QR);
- **в командах управления паролем** лежат в данных задачи BullMQ только зашифрованными `APP_ENCRYPTION_KEY`: шифрует API, расшифровывает воркер;
- в аудит не попадают: у маршрутов, которые их несут, `audited(..., { payload: null })`;
- в логи не попадают.

### Источник аккаунта

`ACCOUNT_SOURCES` получает `phone`, в интерфейсе — «по номеру». У аккаунтов из входа по номеру `client_profile = own`, как у QR.

## 4. Вход по номеру

### Интерфейс

Третья вкладка «По номеру» в диалоге «Добавить аккаунт». Закрытие диалога отменяет вход.

1. **Номер.** Подключение — как в QR: свободный прокси или явное «Напрямую», без выбора по умолчанию «напрямую». Поле номера телефона. Кнопка «Получить код».
2. **Код.**
   - Надпись, куда ушёл код: «в приложение Telegram — сообщением от «Telegram»», «по SMS», «звонком», «на почту».
   - Поле кода с ожидаемой длиной.
   - Кнопка «Отправить ещё раз» активна после таймаута Telegram и подписана следующим способом («Отправить по SMS» и т.п.).
   - Ошибки под полем: «Неверный код», «Код истёк — запросите новый».
3. **Облачный пароль** (если включён). Подсказка, поле пароля. «Неверный пароль» держится до следующей попытки.
4. **Готово.** Открывается карточка нового аккаунта.

### Воркер

Команда `phone.start {loginId, phone, proxyId, adminId}`.
- Нужен свой api_id/api_hash (`telegram.own.*`), иначе `failed`.
- Прокси — только свободный (то же правило, что `isProxyFree`).
- Временный клиент `TelegramClient` в `MemoryStorage` со своим api_id и через выбранный прокси.

Поток:
1. `sendCode`.
   - Если Telegram сразу авторизовал (`sentCodeSuccess`) — к завершению.
   - Иначе событие `code_sent`: тип доставки, длина, следующий тип, таймаут.
2. Сообщения из канала входа:
   - `code` → `signIn`:
     - `PHONE_CODE_INVALID` → `code_invalid`;
     - `PHONE_CODE_EXPIRED` → `code_expired`;
     - `SESSION_PASSWORD_NEEDED` → `password_needed` с подсказкой.
   - `password` → `checkPassword`; `PASSWORD_HASH_INVALID` → `password_invalid` с подсказкой.
   - `resend` → `resendCode` → снова `code_sent`.
   - `cancel` → `cancelCode` → `cancelled`.
3. Общий таймаут — `telegram.qrTimeout`, по его истечении `expired`. Подпись настройки меняется на «Время на вход (QR и по номеру)».

Ошибки (→ `failed` с понятным сообщением):

| Ошибка Telegram | Сообщение |
|---|---|
| `PHONE_NUMBER_INVALID` | «Неверный номер» |
| `PHONE_NUMBER_BANNED` | «Номер заблокирован Telegram» |
| `PHONE_NUMBER_UNOCCUPIED`, требование регистрации | «На этот номер нет аккаунта Telegram — регистрация через панель не поддерживается» |
| `FLOOD_WAIT_N` | «Слишком много попыток — подождите N мин» |
| `PASSWORD_HASH_INVALID` при переборе | «Неверный пароль», вход продолжается |
| `PHONE_PASSWORD_FLOOD` | «Слишком много попыток ввода пароля — подождите» |
| тип доставки `email_required` | «Telegram требует привязать почту для входа — сделайте это в официальном приложении» |
| `sentCodePaymentRequired` | «Telegram требует платный вход для неофициальных приложений — войдите сначала в официальном» |

### Завершение входа (общий модуль для QR и номера)

1. Аккаунт уже в панели → `logOut` новой сессии, `failed` «Этот аккаунт уже есть в панели».
2. Иначе:
   - создаётся аккаунт (`source`, `client_profile = own`);
   - `session_import_enc` — экспортированная session string;
   - `cloud_password_enc` — если пароль вводили.
3. Временный клиент уничтожается: один ключ — один клиент.
4. `onAccountCreated` → менеджер аккаунтов подключает аккаунт.

QR-вход переходит на этот модуль и начинает сохранять введённый облачный пароль.

### API

| Маршрут | Что делает | Аудит |
|---|---|---|
| `POST /phone-login {phone, proxyId}` | Проверяет свой api_id и свободный прокси, ставит `phone.start`, отвечает `{loginId}` | `account.phone.start`, номер в теле допустим |
| `POST /phone-login/:id/code {code}` | Публикует код в канал входа | без тела |
| `POST /phone-login/:id/password {password}` | Публикует пароль в канал входа | без тела |
| `POST /phone-login/:id/resend` | Публикует запрос повторной отправки | без тела |
| `DELETE /phone-login/:id` | Отменяет вход | — |

Прогресс приходит событием `phone.update` в общий SSE-поток.

## 5. Облачный пароль в карточке аккаунта

### Блок «Облачный пароль»

Загружается при открытии карточки командой `account.password.info`. Если аккаунт не подключён — «Аккаунт не подключён».

- **Пароль:** «установлен» или «не установлен», подсказка.
- **Сам пароль:** если панель знает его — скрыт точками и кнопка «Показать»; нажатие запрашивает `GET /accounts/:id/cloud-password` и пишется в аудит. Если не знает — «неизвестен панели».
- **Почта восстановления:**
  - адрес — когда панель знает пароль;
  - иначе «привязана» или «не привязана»;
  - «ожидает подтверждения: a\*\*\*@g\*\*\*.com», если почта не подтверждена.
- **Отложенный сброс:** если `pendingResetDate` задан — красное предупреждение с датой, когда сброс сработает.

### Действия

- **«Установить пароль»** (пароля нет): новый пароль с повтором, подсказка, почта (необязательна).
- **«Сменить пароль»** (пароль есть): текущий пароль спрашивается, только если панель его не знает. Дальше новый пароль с повтором, подсказка, почта (пусто — прежняя остаётся).
- **«Указать текущий»** (пароль есть, панели неизвестен). Воркер проверяет его через `account.getPasswordSettings`; верный — сохраняется.

### Шаг почты

Если указана почта, Telegram отвечает `EMAIL_UNCONFIRMED_N`. Новый пароль при этом уже действует, почта ждёт подтверждения. Следующий шаг — «Код из письма» (длина N):
- «Подтвердить» → `account.confirmPasswordEmail`;
- «Отправить ещё раз» → `account.resendPasswordEmail`;
- «Пропустить» → `account.cancelPasswordEmail`; пароль остаётся установленным, без почты.

### Ошибки

| Ошибка Telegram | Сообщение |
|---|---|
| `PASSWORD_HASH_INVALID` на введённом текущем | «Неверный текущий пароль» |
| `PASSWORD_HASH_INVALID` на сохранённом | Сохранённый пароль стирается: «Сохранённый пароль не подошёл — его сменили вне панели, укажите текущий» |
| `SESSION_TOO_FRESH_N`, `PASSWORD_TOO_FRESH_N` | «Telegram пока не даёт менять пароль с этой сессии — подождите N ч» |
| `EMAIL_INVALID` | «Неверная почта» |
| `CODE_INVALID` | «Неверный код» |
| `EMAIL_HASH_EXPIRED` | «Код истёк — отправьте снова» |
| аккаунт не подключён | 409 «Аккаунт не подключён» |

### API

Секреты в задачу воркеру уходят зашифрованными. Маршруты с паролем или кодом пишутся в аудит без тела.

| Маршрут | Команда воркера | Ответ |
|---|---|---|
| `GET /accounts/:id/cloud-password/info` | `account.password.info` | состояние |
| `GET /accounts/:id/cloud-password` | — | расшифрованный пароль из БД; аудит `account.cloud_password.read` |
| `POST /accounts/:id/cloud-password/verify {password}` | `account.password.verify` | — |
| `PUT /accounts/:id/cloud-password {currentPassword?, newPassword, hint?, email?}` | `account.password.set` | `{ ok: true }` или `{ emailCodeNeeded: { pattern, length } }` |
| `POST /accounts/:id/cloud-password/email {action: 'confirm', code} \| {action: 'resend'} \| {action: 'cancel'}` | `account.password.email` | — |

Пароль в БД пишет воркер — после успеха в `verify` и `set`.

## 6. Контракты (`packages/shared`)

- **Команды:** `phone.start`, `account.password.info`, `account.password.verify`, `account.password.set`, `account.password.email`. Поля с секретами — `…Enc`, шифротекст. Результаты структурные: `{ error: 'not_running' | 'wrong_password' | 'stale_password' | 'too_fresh', retryAfterSec? }` и т.п., а не исключения.
- **Канал входа** `accs:login:<id>`. Сообщения: `{type:'code', code}`, `{type:'password', password}`, `{type:'resend'}`, `{type:'cancel'}`.
- **Событие** `phone.update {loginId, state, …}`:
  - состояния `code_sent`, `code_invalid`, `code_expired`, `password_needed`, `password_invalid`, `done`, `failed`, `expired`, `cancelled`;
  - поля `deliveryType`, `codeLength`, `nextType`, `retryAfterSec`, `hint`, `accountId`, `message`.

## 7. Тестирование

Telegram в тестах не трогаем — сценарные фейки клиента, как у QR.

- **Воркер, вход по номеру:**
  - неверный код → верный → неверный пароль → верный → аккаунт `source=phone` с зашифрованным паролем;
  - повторная отправка, отмена, таймаут;
  - дубликат → выход новой сессии;
  - каждое сообщение таблицы ошибок;
  - `sentCodeSuccess`;
  - QR сохраняет введённый пароль.
- **Воркер, облачный пароль:**
  - состояние при известном и неизвестном пароле;
  - `verify` — верный и неверный;
  - `set` — установить, сменить с сохранённым текущим, устаревший сохранённый;
  - шаг почты — подтвердить, отправить снова, отменить;
  - `SESSION_TOO_FRESH`.
- **API:**
  - нужен свой api_id и свободный прокси;
  - код и пароли не попадают в аудит;
  - в данных задач только шифротекст;
  - «Показать» пишется в аудит;
  - 409 для неподключённого аккаунта.
- **Веб:**
  - вкладка «По номеру» во всех состояниях (подписи способов доставки, «Отправить ещё раз» после таймаута, подсказка и «неверный пароль»);
  - блок облачного пароля: отображение, предупреждение о сбросе, «Показать», установка с шагом почты и «Пропустить».
- **e2e:** вкладка «По номеру» без своего api_id показывает понятную ошибку.
- **Живая проверка:**
  - вход по номеру на аккаунте владельца с одной сессией Desktop — код приходит в Desktop; перед этим аккаунт удаляется из панели без выхода;
  - смена облачного пароля — только на аккаунте, который назовёт владелец.

## 8. Вне объёма

- Снятие облачного пароля.
- Отмена отложенного сброса (`account.declinePasswordReset`): в карточке только предупреждение.
- Регистрация новых номеров.
- Привязка почты для входа (login email).
- Восстановление пароля через почту.

## 9. Риски

- **Свежесть сессии.** Telegram может не давать менять пароль с новой сессии (`SESSION_TOO_FRESH_N`). Это касается как раз аккаунтов, только что добавленных по номеру или QR. Панель показывает срок ожидания; обойти нельзя.
- **Неподтверждённая почта.** Что новый пароль действует до подтверждения почты, следует из протокола (`EMAIL_UNCONFIRMED_N` после `updatePasswordSettings`). Проверяется вживую на аккаунте владельца.
- **Профиль устройства.** У QR-аккаунтов профиль устройства при входе и при последующих сессиях не совпадает (отложено из ревью плана 2). Вход по номеру использует тот же профиль, что и QR, — исправлять обоим сразу, отдельно.
- **Занятый слот очереди.** Вход по номеру, как и QR, держит слот очереди команд на всё время входа (отложено из ревью плана 2).
